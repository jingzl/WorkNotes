# 1. 概述

## 1.1 什么是ClaudeCode
Claude Code 是由 Anthropic 公司推出的 AI 驱动命令行编程工具，通过自然语言对话完成代码编写、调试、重构等开发任务。它不是简单的代码补全工具，而是一个能够**理解整个代码库、跨文件操作、自主规划执行步骤**的智能代理。
**核心能力**
- 代码读写	读取整个代码库，编辑多文件
- 命令执行	运行终端命令、构建项目、启动服务
- 工具集成	Git、MCP 扩展、浏览器、文件系统
- 主动规划	任务拆解、步骤执行、结果验证
- 持久记忆	跨会话记住项目规则和上下文

## 1.2 核心概念

**1）上下文窗口**
可将其理解为 Claude 的临时工作记忆。它能容纳海量信息，但无法一次性承载全部内容。这也是其自主执行能力的核心原理：无需把完整代码库全部载入记忆，就能通过合理策略在代码库中精准检索所需答案。
**2）默认请求许可**
Claude Code 在执行指令、修改代码文件前，都会主动向你发起确认请求。无论你是全程手动把控，还是交由工具自主运行，始终由你掌握全部操作主导权。

# 2. 工作原理
核心运行逻辑，核心是一个递归的 Agentic Loop。
## 2.1 核心运行： Agentic Loop​
- **输入指令**：你向 Claude Code 输入需求提示词。​
- **搜集所需信息**：它结合大模型分析需求，调取完成任务必备相关内容，模型会返回文本内容或可执行的工具调用指令。​
- **执行实际操作**：依据指令做出对应行为，例如修改代码文件、运行终端命令等。​
- **结果核验判定**：自动校验执行结果，判断是否达成你最初提出的需求目标。​
- **闭环循环**​ 
	- 结果达标：任务结束，等待你的下一条指令​
	- 结果未达标：重新进入循环流程，反复执行操作、核验，直至任务完成且结果无误​​
**人工干预权限**： 整个运行过程中，你随时可以补充信息、中断进程、引导模型思路，把控最终任务走向。

## 2.2 上下文窗口机制​
上下文窗口决定了它能留存、回看的内容上限，包含对话记录、代码文件内容、命令执行日志等所有信息。
一旦达到存储上限，Claude Code 会 自动压缩整理会话内容 ：剔除无用信息、精简总结冗余内容，主动释放上下文空间，保证程序正常运行。

## 2.3 核心支柱：工具调用能力
- ​普通 AI 助手仅支持纯文字输入输出，无中间实操能力；而工具调用是智能Agent的核心根基。​
- 借助各类内置工具，Claude Code 可自主判断时机调用功能推进任务，例如读取文件、联网检索等。​ 
- 还支持语义检索，精准判断调用对应工具，并获取工具执行结果。​ ​

## 2.4 权限运行模式​
默认状态下，修改文件、运行终端命令**必须提前征得你的手动确认** ，按下 Shift+Tab 可快速切换运行模式：​
  - 自动编辑模式 ：自动同意文件修改操作，运行命令依旧需要手动授权​
  - 规划模式 ：仅使用只读类工具，先梳理完整执行方案，再正式开始执行任务​
**重要提醒**： 切勿随意关闭权限校验、放任其自由执行命令，一旦出现逻辑错误，极易引发难以察觉的代码故障与运行风险。

# 3. CLAUDE.md 文件
## 3.1 主要作用
是 Claude Code 最实用的功能之一，相当于给项目搭建 长期专属记忆。
- ​项目内没有该文件时，每次启动 Claude Code 都要从零开始：重新遍历代码库、梳理项目依赖、梳理已完成功能，还容易自行主观猜测项目规范，很难精准对齐你的开发思路。
- claude.md 是放在 项目根目录 的 Markdown 文件，每次开启会话都会被自动读取，等同于项目专属的开发指引手册。​ 
- 文件内的所有内容，会自动追加到你的每一条提示词中，潜移默化统一开发规范。​
- 快捷生成指令：输入 /init ，即可让 Claude 自动根据当前项目结构生成对应的 claude.md 文件。

## 3.2 文件内容示例
以 Next.js 15 项目为例，可写入这类统一规则：​ 
- 技术栈：采用 App Router、Tailwind CSS、Drizzle ORM​ 
- 运行规范：本地启动开发服务、执行测试、代码格式化​ 
- 代码风格：缩进使用 2 个空格，优先使用具名导出​ 
- 目录规范：所有接口路由统一放在 app/api 目录​ 
- 开发原则：优先使用服务端动作，尽量少用传统接口路由​ 
写入后，你让它新建 React 组件、编写业务代码时，会自动沿用这套规范，无需反复重复叮嘱。

## 3.3 记忆文件层级划分​
**项目级 claude.md**​ 
- 存放于项目根目录，跟随项目版本管理同步提交， 团队全员共用 ，统一团队项目开发标准。​ 
**用户级 claude.md​** 
- 存放在个人配置文件夹中，仅对本人生效， 全局所有项目通用 。可填写个人编码习惯、注释风格、固定开发偏好等私人设定。

## 3.4 使用技巧​
- **固定开发习惯** ：若你需要强制统一写法（如优先用服务端动作），可直接让 Claude 将该规则存入记忆，后续打开项目自动生效。​ 
- **引用项目文档** ：想让它读取项目内指定文档作为参考，直接用 @+文件路径 即可快速引用。​
- **精简编写原则**：新项目初期建议先不创建该文件，在使用过程中记录需要反复纠正的开发要求，最后再整理写入，保证文件简洁精炼，只留存必要规则。

## 3.5 特别分析
参考：
https://mp.weixin.qq.com/s/lpnj98fYBk1cf_TCFPwxYg

**问题：**
Claude Code 用了半年，你的 CLAUDE.md 现在多少行了？"两千多行吧，"他答得挺顺，"项目约定、代码规范、踩过的坑，想到什么往里加。"
**分析：**
CLAUDE.md 每次会话自动加载进上下文，你写多少，模型每轮就读多少。两千行两万多 token，一次会话来回几十轮，光重读这一个文件就是几十万 token。更糟的是，真正高频用到的可能就二三十行，剩下全是噪声，把那二三十行也淹了。
CLAUDE.md 不是写出来的，是维护出来的。
**1）CLAUDE.md 不是越全越好，它是每轮都要付的"常驻成本"，在每一轮对话里重复付费的。**
CLAUDE.md 是**会话启动时就自动注入上下文**的，它不是按需读取，是常驻。
这跟 skill 是两套完全不同的加载逻辑。skill（SKILL.md）走的是渐进式按需加载：默认只把名字和一句话描述放进上下文，模型判断这次任务用得上，才把完整内容读进来。一个不常用的复杂流程放进 skill，不用的时候它几乎不占上下文；同样的内容塞进 CLAUDE.md，哪怕一个月用不上一次，也得每轮陪读。
CLAUDE.md太大，直接导致① token大量消耗。② 注意力被稀释。模型的注意力是有限的，把二三十条真正高频的硬约束，和一千多行"某次调试随手记的临时笔记"混在一起，那二三十条就被埋了。
![](../../assets/ClaudeCode-20260627220616.png)

**2）什么才该进 CLAUDE.md：高频、稳定、跨会话**
一条信息该不该进 CLAUDE.md，看三个条件，三个都满足才进：
**高频。** 这条信息是不是几乎每次会话都会用到。比如项目的构建命令、测试怎么跑、代码风格约定，这些基本每次都碰得到，进。一个季度才用一次的发布流程，不进。
**稳定。** 这条信息是不是长期不变。项目的目录结构约定、技术栈选型，半年都不会动，进。当前正在调的某个 bug、这周的临时分支策略，下周就过时了，不进，写进去就是给未来的自己埋雷。
**跨会话。** 这条信息是不是换个会话还需要。架构上的"反直觉陷阱"，比如"这个服务看着是无状态的，其实依赖一个全局缓存，改它要小心"，这种每个新会话都得知道，进。某次对话里临时确定的一个参数，这次说清楚就行，不进。
三个条件像一个漏斗，能同时穿过的东西其实不多。我自己维护的项目级 CLAUDE.md，绝大多数控制在一百行出头，再多就要警惕了。
![](../../assets/ClaudeCode-20260627220944.png)

**3）分层维护：项目级、全局级、skill 级各管一段**
**全局级，`~/.claude/CLAUDE.md`。** 这是你个人的、跨所有项目的偏好。比如"回答用中文""提交信息别写废话""默认用 pytest 不用 unittest"。它只在你这台机器上生效，不进任何项目的 git。放这层的判断标准是：这条偏好换个项目还成立吗？成立，就该上提到全局，别在每个项目的 CLAUDE.md 里抄一遍。

**项目级，项目根目录的 `./CLAUDE.md`。** 这是这个项目特有的、要跟团队共享的约定。它进 git，团队每个人拉下来都生效。构建命令、目录约定、这个项目特有的架构陷阱，放这层。判断标准反过来：这条只对这个项目成立、且队友也需要知道吗？是，就放项目级并提交。

**skill 级，`SKILL.md`。** 前面说的那些低频但成套的专项流程，放这层，按需加载，不占常驻上下文。

这三层之外还有两个常用的补充手段。一个是**子目录 CLAUDE.md**：大仓库里某个子模块有自己特殊的约定，可以在那个子目录单独放一份，只有在那个子树里干活时才加载，不污染主上下文。另一个是 **`@路径` 引入**：CLAUDE.md 里可以用 `@docs/architecture.md` 这种写法把外部文件按需带进来，既保持主文件干净，又能在需要时引用大块内容。
![](../../assets/ClaudeCode-20260627221306.png)

**4）定期精简：什么信号说明它该瘦身了**
**信号一，行数越界。** 项目级 CLAUDE.md 超过两三百行，先别急着加新的，回头看看有没有过时的。经验阈值是项目级一百多行、全局级几十行，超了就该警惕。
**信号二，模型反复忽略某条指令。** 这是个特别强的信号，前面那个备份的 case 就是。如果你发现某条明明写了的约定，模型老是不遵守，先别怪模型，大概率是它被埋太深了。要么把它提到最前面的硬约束区，要么说明它已经不重要了可以删。
**信号三，出现"上次那个 bug""临时先这样"这类字眼。** 这些都是会过时的临时信息，混进了常驻文件。定期搜一遍这类词，基本都能清掉一批。
**信号四，同一件事写了两遍。** 文件长了就容易重复表达，重复的内容不光占地方，还可能前后矛盾，让模型无所适从。

精简的手法也简单：高频硬约束往顶部提，单独成段、显眼；低频成套的流程下沉成 skill；过时的、临时的直接删；大段文档挪出去用 `@` 引。精简不是一次性的活，大概每两三周会扫一遍主力项目的 CLAUDE.md，每次都能删掉三五十行，删完模型的表现反而更稳。

# 4. 标准流程

标准流程： 调研探索 → 制定方案 → 编写代码 → 提交代码。
## 4.1 规划方案​
- 规划模式下 仅只读文件，不做修改 ，只会读取项目代码、梳理实现思路​ 
- 开启方式：按下 **Shift+Tab** ，输入框上方显示规划模式即成功​ 
- 使用示例需求：在图片上传流程中新增格式转换功能可让 AI 自主定位流程节点、判断是否需要安装新依赖、梳理完整实现思路​ 
- 流程优势：AI 会读取相关代码、查阅相关资料，输出完整执行方案；你先行审核，不满意可直接要求增补、修改内容。 此阶段是最佳修正时机，全程还未编写任何代码
## 4.2 编写代码​
- 方案确认无误后，点击同意执行，AI 自动按清单逐项落地开发​ 
- 可提前设置文件修改权限：自动确认编辑 或 每次修改手动确认​ 
- AI 会主动排查代码问题，过程中依旧可随时调整思路、纠正偏差​ 
- 规划模式留存完整思考逻辑，后续开发决策更贴合项目需求
## 4.3 提升方案准确率实用技巧​ 
- 需求标准写明确，让 AI 清晰判定合格交付标准​ 
- 配齐辅助工具减少反复沟通​ 
	- 开发网页界面时安装配套浏览器插件，支持 AI 操控页面实测 UI 效果​ 
	- 项目内置完备测试用例，可让 AI 自测校验，也可让 AI 自主编写测试代码​ 
	- 统一测试判定标准，避免出现无效校验结果​ 
- 高频问题固化方案遇到反复出现的同类问题，直接让 AI 把解决办法存入 .claude.md 记忆文件，永久复用
## 4.4 提交代码前​ 
- 人工自测验证功能无误​ 
- 调用代码审查工具，完成代码自查评审​ 
- 让 AI 按照你的习惯风格自动生成规范提交备注​ 
- 提交推送代码，开启下一项功能开发
## 4.5 工作流完整价值总结​ 
- 探索调研：补齐项目所需全部上下文信息​ 
- 方案规划：定下执行标准与验收依据​ 
- 代码编写：人机协同打磨，敲定最终实现效果​
- 提交入库：完成代码审核与版本推送，无缝衔接下一开发任务

# 5. Claude Code的上下文管理
## 5.1 什么是上下文
​上下文就是 Claude Code 的 运行内存 。你读取的文件、执行的命令、发送的对话消息，都会占用上下文窗口空间。可以把它理解为模型的记忆存储空间，所有交互行为都会不断往里累加内容，而存储空间存在上限，做好优化十分关键。
## 5.2 自动压缩机制​
当内容快要达到上下文上限时，系统会 自动执行压缩整理 ：提炼留存关键信息，剔除无用的工具调用日志与冗余结果，释放大量内存空间。⚠️ 注意：自动压缩可能会丢失部分过往对话细节。
## 5.3 手动上下文管理指令
- /compact 手动压缩​ 
压缩当前会话所有历史内容，精简冗余信息，保留核心工作记录，适合想腾出空间、又不想清空过往记录时使用。​
- /clear 清空上下文​ 
彻底清除全部会话记忆，从零全新开始，完全摒弃之前所有操作记录。​
- /context 查看上下文状态​ 
直观查看当前内存占用大小、各类内容占比，还有可视化数据图表，清晰掌握资源使用情况。​ ​
## 5.4 使用场景取舍​ 
- 开发同一功能、临近超限 ：执行压缩，保留当前业务相关上下文，保证开发连贯​ 
- 完成旧功能、开启新需求 ：直接清空上下文，避免旧内容造成思路干扰、判断偏差​ 
- 长期通用固定规则 ：写入 .claude.md 文件，脱离临时上下文永久生效，不用重复告知
## 5.5 优化上下文实用技巧​ 
- 提示词务必写详尽明确 简略模糊的指令看似简短，反而会让模型主动翻阅大量代码、自主推演思考，额外消耗更多上下文资源；一两句话把需求说清楚，反而更省空间。​ 
- 关停无关 MCP 服务 MCP 服务器会默认把所有可用工具载入上下文，项目用不到的 MCP 服务建议直接关闭。​ 
- 优先使用 Skill 工具 功能和 MCP 类似，但不会将全部内容载入上下文，有效节省内存。​ 
- 巧用子代理分担任务 子代理和主代理相互独立，拥有专属独立上下文窗口，可并行运行。查询类简单任务（如查找认证接口地址等）交给子代理处理，仅把最终结果汇总给主代理，大幅减轻主上下文负担。​ 
## 5.6 核心总结​ 
高效用好 Claude Code 的关键就是管好上下文：长会话精简用 /compact ，换新需求重置用 /clear ；需求描述精准清晰，定期查看占用状态；非核心查询任务交给子代理分流，最大化利用内存空间。

# 6. ClaudeCode里的MCP
## 6.1 MCP基础定义​
MCP（Model Context Protocol 模型上下文协议）​是一套开放通用标准，作用是让 Claude Code能够无缝对接各类外部工具与数据源。​你提出需求时，它可自动判断调用对应外部工具，精准理解并完成任务。
## 6.2 MCP核心价值​
使用Claude Code开发时，大量业务相关数据并不在本地代码内，而是存放在数据库、办公协作软件、开源仓库等外部平台，MCP 就是打通这些外部资源的核心桥梁。同时 工具调用 是AI Agent的核心能力，区别于普通AI仅纯文字问答，Claude Code 可借助各类工具执行实际操作，落地完整任务。
## 6.3 实际应用场景​
团队使用 Linear 项目管理工具：接入对应 Linear MCP 服务，可直接同步同步项目工单、任务详情​
查阅依赖库最新文档：接入文档类 MCP 服务，快速获取官方最新技术资料​。
更多第三方连接器可在官网 https://claude.com/connectors 查找​。
## 6.4 MCP服务添加与分类​
添加命令：使用 **claude mcp add** 快速接入MCP服务​
两大服务类型​
- **HTTP 服务端**：对接云端远程第三方服务，通过网络实现连接​
- **Stdio 本地服务端**：运行在你本机电脑的本地进程服务​
会话内管理：在Claude Code中输入 **/mcp** ，可查看已连接服务、运行状态，一键停用闲置服务​。
## 6.5 MCP三种作用域​
- 本地作用域 ：仅在当前项目生效​
- 用户全局作用域 ：绑定个人账号，所有项目均可通用​
- 项目级作用域 ：通过 project.mcp.json 文件配置并提交版本库，团队所有成员拉取项目后自动同步配置，统一开发环境​
## 6.6 上下文优化避坑要点​
**弊端**：即便暂时不用，已配置的MCP服务也会把工具定义信息占用上下文空间，配置过多会挤占可用内存​
**优化方案​**：
- 及时停用长期闲置的MCP服务，减少资源占用​
- 有对应CLI命令行工具（GitHub、AWS等）优先用CLI，比MCP更节省上下文​
- 优先使用Skill能力：仅将名称与简介载入上下文，需要用时再完整加载，轻量化更省空间​
**自动适配机制​**：
当MCP工具占用上下文超过10%，Claude Code会自动切换为 工具检索模式 ，按需查找调用工具，但该模式执行稳定性会有所下降​。
## 6.7 核心总结​
MCP实现Claude Code与外部工具、业务数据源互联互通​
借助命令快速添加服务，通过配置文件实现团队统一同步​
日常维护及时清理无用服务，严控上下文占用​
合理搭配CLI工具与Skill能力，平衡功能实用性与运行效率
# 7. ClaudeCode里的Hooks
Prompt、CLAUDE.md、skill 都是在“尽量引导 Claude”。​Hook 则是在“强制某件事按规则执行”。
## 7.1 ​Hooks是什么​
hooks可以在 Claude Code 整个运行生命周期的指定节点自动执行命令 。​
它和其他功能最大区别： 执行结果确定、必定触发 。​
举例：​
你写在 `claude.md` 里让它改完文件自动格式化，偶尔会失效；​
但写成hooks规则， **每次都会强制执行，毫无例外**。
## 7.2 常用实战场景​
- 文件修改完成后自动格式化代码​ 
- 记录所有执行命令，满足合规审计需求​ 
- 拦截高危操作，禁止修改生产环境配置文件​ 
- 任务执行完毕自动推送消息通知
## 7.3 配置入口与基础写法​ 
所有hooks统一在 `.claude/settings.json` 中配置​ 配置三要素：​ 
- 选定触发事件​ 
- 可选设置匹配规则，限定生效工具​ 
- 填写需要自动运行的终端命令
## 7.4 五大核心触发时机​ 
- 用户提交提示词前：提交指令后、模型开始处理前触发​ 
- 工具调用前置（pre tool use）：调用任何工具 之前 执行​ 
- 工具调用后置（post tool use）：工具执行 完成后 触发​ 
- 消息通知触发 ：Claude 推送通知时运行​ 
- 会话结束触发 ：模型完成全部应答后执行
## 7.5 高频用法
1. 改文件自动格式化（最常用）
选用工具调用后置hooks。匹配规则设为：单文件编辑、批量编辑。只要 Claude 修改代码文件就自动触发，可根据文件后缀执行对应格式化命令。
2. 拦截高危操作（强约束管控）
前置hooks可直接阻止工具执行​。hooks通过标准输入获取工具名称与入参JSON，通过 **退出码** 控制行为：​
- 退出码 0 ：放行，正常执行操作​ 
- 退出码 2 ：直接阻断操作，错误信息同步返回给 Claude​ 模型会明确知晓拦截原因并自行调整行为​
**适用管控场景**：​
- 禁止写入生产配置目录​ 
- 拦截含 rm -rf 等高风险删除命令​ 
- 禁止直接向主干分支提交代码​ 
可强制落地团队硬性规范，而非仅口头提醒。
## 7.6 作用域​
- 该配置属于 **项目级配置** ，可提交到代码仓库​ 
- 团队所有成员拉取项目后，自动同步全套hooks规则​ 
- 搭配项目环境变量，可直接调用项目内脚本，不受当前工作目录影响​ ​
## 7.7 使用总结​
- 后置hooks ：用来做自动格式化、操作日志记录​ 
- 前置hooks ：用来拦截危险行为、强制校验规范​ 
- 统一在项目配置文件编写并入库，全员统一生效​ 
- 凡是 必须次次执行、绝对不能遗漏 的操作，不要写在提示词里，直接配置hooks实现强制管控
